# WSGM 2.0 decision record

Status: authoritative lean decisions, updated 2026-08-31

This file records choices that implementation must not reopen accidentally. It supersedes the
earlier enterprise-style package, evidence, trust, traceability, and release-governance design.
Verified device facts remain in [`claw-8-a2vm-plugin.md`](./claw-8-a2vm-plugin.md).

## Decision standard

A structural mechanism belongs in WSGM 2.0 only when at least one of these is true:

- It directly implements a fixed feature.
- An external API, public package contract, process lifetime, or packaging requirement forces the
  boundary.
- It prevents a demonstrated hardware, input, Steam, shell, update, or recovery failure.
- A current community plugin developer needs it to build, run, diagnose, or distribute a plugin.

Future ecosystem scale, formal governance, theoretical hostile administrators, and generated proof
of process are not sufficient reasons.

## Locked decisions

### D01 — The feature scope is not reduced

The Device SDK/plugins, complete Claw support, Steam Deck/Xbox 360/DualShock 4 targets, per-app
targets, physical glyphs, RTSS/native QAM, AutoTDP, Device Lab, and final overlay all remain required
2.0 outcomes. Simplification changes their implementation and delivery machinery, not their presence.

### D02 — Exactly one installed Device Plugin

Zero plugins starts core WSGM without Device Integration. One plugin is validated and used. More
than one plugin refuses normal startup before matching/loading and lists every conflict. There is no
ranking, selection, priority, enablement collection, or multi-plugin coordination.

Recovery/setup/update/uninstall and `--restore-shell` remain available. Developer plugins occupy
the same logical slot. Updates stage elsewhere and atomically replace the slot.

### D03 — The sole Device Plugin runs in WSGM

WSGM runs on CoreCLR and loads the one installed plugin into a package-local collectible load
context. One lifecycle adapter connects it directly to the coordinator. There is no DeviceHost,
pipe protocol, input ring, process supervision, wire negotiation, duplicate package loader, or
rollback mode for an unverifiable old host. A plugin fault remains feature-local and the session's
bounded make-safe/unload path handles recovery.

### D04 — Installed plugins are deliberately trusted hardware code

The sole normal plugin lives in an administrator-protected directory and may inherit WSGM's
elevation. An unprivileged process must not be able to replace it. Installation is explicit and
WSGM never downloads plugins at runtime.

There are no reviewed/signed/sideloaded/developer runtime trust tiers, publisher promotion,
certificate rotation workflow, WSGM revocation list, or independent plugin rollback engine.
Developer mode is an explicit local hardware-development session.

### D05 — The SDK is thin and public

The SDK defines lifecycle, semantic capabilities, canonical input/output, diagnostics, a small
manifest, TestKit, and bounded manifest/glyph validation. Device Lab owns scaffolding and archive
packaging. The SDK does not prescribe a plugin's internal
transport/protocol/layout/policy hierarchy or require generators, evidence locks, and promotion
metadata.

### D06 — Exact compatibility is preferred

WSGM, the SDK, Device Lab, and the installed plugin are one compatible composition.
2.0 requires exact equality of the single integer API version rather than forward/backward
negotiation across a compatibility matrix. Unknown fields may be ignored where normal JSON
tolerance is useful, but no release may depend on mixed independently updated platform components.

### D07 — Device Lab remains a feature and stops being an authority

Device Lab retains GUI and CLI inventory, capture, correlation, known matching, read probes,
attended semantic actions, scaffold, fixture, local run, validation, and pack workflows. These are
implemented by one application and shared internal services.

It does not grant package trust, promote evidence grades, execute imported recipes, maintain an
ecosystem database, or require a separate ProbeHost/hash-admission protocol.

### D08 — Plugins own hardware; WSGM owns semantics

Plugins own identity, transports, ranges, validation, write/readback, restoration, resource
conflicts, hotplug, suspend/resume, physical input normalization, output encoding, OEM sources, and
static glyph data. WSGM owns semantic UI/state, profiles, plugin runtime lifetime, virtual targets,
HidHide, input arbitration, RTSS, CEF/QAM, AutoTDP, and OEM action mapping.

WSGM exposes no generic raw or privileged WMI/HID/EC/IOCTL/ACPI/MMIO/MSR/serial broker.

### D09 — Device lifecycle spans the WSGM run

The owner is the one resident `ShellSession` process. Device Integration starts asynchronously and
survives Desktop/Game Mode transitions, games, and Steam restarts. Only owner exit or the Settings
master toggle intentionally ends the device cycle. A host crash is a fault within that cycle.

`--settings` edits configuration only. `--overlay-test` uses simulated capabilities and touches no
hardware, plugin runtime, target, or HidHide state.

### D10 — Capabilities stay practical

Capability descriptors contain what the UI needs: stable ID/role, display information, supported
operations, range/step/unit or choices, and availability. State contains the current value,
observation time/freshness, command progress, and an ordinary unavailable/error reason.

Do not add evidence grades, review state, package trust, desired-state generations, and workflow
status to runtime DTOs unless a concrete feature consumes them.

### D11 — Hardware safety is mandatory and local

Exact identity/firmware gates, current bounds, serialized vendor calls, original-state capture,
readback, targeted rollback, and unresolved recovery records remain. The plugin revalidates every
hardware command. Persistent user intent such as Claw RGB is not incorrectly restored like a
temporary diagnostic change.

### D12 — VIIPER is the one virtual-controller backend

Required targets are Steam Deck Composite, Xbox 360, and DualShock 4. Only one exists at a time.
WSGM stores a global target and direct per-application overrides. Plugins never call VIIPER.

VIIPER carries the complete Steam Deck frame, including four rear controls and stick touch, through
usbip-win2's signed driver. It is bound directly in WSGM; there is no ControllerHost or alternate
backend framework. Controller management remains required, so missing Xbox 360 or DualShock 4
encoders are completed in this backend rather than deleting the targets.

### D13 — HidHide is an owned delta

WSGM adds and removes only its HidHide entries. It never normalizes external configuration.
Controller disable/stop neutralizes the target, lets the plugin release/restore physical input, then
removes the target and WSGM-owned HidHide state.

### D14 — Managed WSGM UI input and fallback both stay

A healthy plugin source navigates WSGM surfaces directly. Local UI capture neutralizes gameplay
output and waits for used controls to release. Steam's native QAM continues receiving the virtual
target. SDL plus the Steam Input lease remains the fallback for unmanaged/degraded input and
separate per-game launch leases.

### D15 — WSGM is not a general remapper

No arbitrary standard-controller, gyro, touch, macro, script, or executable mapping. Only logical
OEM controls may select from a WSGM-owned allowlist of overlay, QAM, system, profile, and supported
target-button actions.

### D16 — Native Steam UI is restored narrowly

One persistent Steam CDP owner supports built-in probe/apply/verify/remove patches with reconnect.
No global SteamOS/Deck spoof, external patch packages, arbitrary evaluation API, or plugin-supplied
Steam code. Each failure retains native Valve UI and does not disable unrelated patches.

**Supplying a backend Steam is missing on Windows is in scope, and is not the forbidden spoof.**
Live probing on 2026-08-30 established that Valve's own performance, audio and Bluetooth surfaces
ship in the Windows client and are inert only because nothing answers behind them. Filling one of
those seams is narrow, reversible, and affects exactly the surface it names. The forbidden thing is
the global claim, not the local answer, and the difference is not academic:
`networkManagementAvailable` is literally `return TS.IS_STEAMOS`, so overriding that one getter and
setting the constant it reads produce the same Wi-Fi row while one touches a single store and the
other changes unrelated client behaviour everywhere.

Four gates, and what may be done to each:

| Gate | Example | Allowed response |
| --- | --- | --- |
| Absent JS namespace | `SteamClient.System.Perf`, `System.Audio` | Supply it |
| Absent RPC response | `SteamOSService/State/Manager` | Supply it |
| RPC stub with no backend | `BluetoothManagerService` | Replace the stub's methods |
| Deck-only store getter | `networkManagementAvailable` | Override that one getter |
| Global platform constant | `TS.IS_STEAMOS` | **Never** |

Each supplied backend is a patch like any other: its own id, fingerprint, verification, removal, and
kill switch, so a client whose shape changes loses one row and nothing else.

### D17 — QAM and overlay share services

Native QAM projects TDP, frame limit, RTSS overlay level, performance/profile state, controller
target, and supported AutoTDP controls. The overlay is the complete surface. Both call the same
device/controller/RTSS/AutoTDP services.

OEM2 toggles native QAM when healthy; otherwise one press opens the WSGM Device page once. It does
not launch Steam, queue a later action, or replay a press.

### D18 — RTSS remains useful without Device Integration

Frame limit and overlay-level controls belong to WSGM/RTSS and continue when Device Integration is
off. Plugin telemetry simply adds metrics when available.

### D19 — AutoTDP is frametime-driven and direct

AutoTDP is one session service over the primary power capability. It raises power promptly on
sustained misses, lowers through settled probes, restores after a failed probe, handles caps/menus,
learns per application/context, pauses for manual TDP, serializes writes, and restores the
underlying manual/profile value on stop.

CPU/GPU utilization is not a policy input. Start with the simplest deterministic controller that
passes trace replay and hardware behavior; add models only when evidence demonstrates a gap.

### D20 — Glyph data belongs to the plugin; adapters belong to WSGM

The sole active plugin ships static artwork and a declarative physical control map. WSGM validates
and renders it. WSGM alone owns Steam selectors/injection and Avalonia adaptation. Plugins supply no
runtime CSS/JS/XAML/URLs/commands.

Physical presentation remains independent of virtual target and bindings. Automatic exact selection
falls back to native Steam/generic WSGM, and manual profile selection remains diagnostic.

### D21 — The overlay information architecture (revised 2026-09-01)

The overlay is one top-edge **sheet** that replaced the right-side panel and the bottom taskbar
(the maintainer's 2.0 visual direction: SteamOS edge map — left/right Steam, top/bottom WSGM — with
the game strip left visible below the sheet as the tap-to-close target). Destinations, in strip
order: **Quick access** (the home root: rows the user pins from any other root), **Session**, Steam,
optional Device, **Tools** and **Power**; the Open apps strip and the status pills (tray, eject,
audio, radios, battery, clock) live in the sheet. Device still contains overview, profiles,
power/thermals, controller/motion, OEM controls, lighting/features, glyph preview, diagnostics, and
recovery. Settings contains WSGM ownership/startup/integration/logging/update policy only.

### D22 — Shutdown has one bounded owner

The authoritative WSGM process coordinates device/controller restoration before CEF/RTSS and final
exit. Normal/update/logoff/uninstall paths use one outer deadline appropriate to the path, report a
compact clean/unverified/timed-out/failed result, and preserve unresolved recovery state.

The uninstaller may remove WSGM-owned virtual/HidHide state after graceful failure. It never invents
hardware restoration without the plugin.

### D22b — Settings holds settings; the overlay holds device control

WSGM Settings never becomes a device control surface. Hardware controls and profile selection live in
the overlay's Device destination; Settings owns startup, diagnostics, top-level ownership policy,
plugin-declared settings, and the authoring of named profiles.

The line is not a judgement call. Changing a **setting** configures how the plugin or WSGM behaves
and WSGM stores the value; changing a **capability** writes hardware state and the device holds it. A
control that writes to the device when the user moves it is a capability, however much it reads like
a preference.

Authoring is not control: defining a named fan curve or RGB profile writes no hardware, which is why
it belongs on the surface that has a mouse. Selecting which definition is active is control, and
stays in the overlay.

This was enforced in code and stated to the user in `DeviceOwnershipPage.axaml` long before it was
written down anywhere, which is precisely why it kept being proposed away.

### D23 — Dependencies and updates are explicit

Plugins and runtime code do not install/repair drivers, providers, services, tasks, certificates, or
helpers. The WSGM installer may ship the pinned VIIPER/usbip-win2/HidHide composition and first-party plugin.
External/OEM prerequisites remain user-installed. Updates replace WSGM and the one plugin as an
atomic compatible composition.

### D24 — Validation targets failure-prone behavior

Unit tests cover pure parsing, decisions, bounds, lifecycle, cleanup ownership, AutoTDP replay, and
known regressions. Integration tests cover in-process runtime faults/unload and built-in Steam/RTSS
adapters. Hardware/live checks cover the behavior that fixtures cannot prove.

Generated requirement traceability, a universal fault scheduler, exhaustive schema fuzz matrices,
and tests for every theoretical DTO ordering are not release requirements.

### D25 — License and third-party obligations remain ordinary

WSGM is GPL-3.0-or-later. Shipped VIIPER, usbip-win2, HidHide, glyph artwork, and other third-party
artifacts retain their required notices. Protocol facts learned from references are facts; copied
expression follows its source license. A license notice and source revision are sufficient for
ordinary plugin assets; no provenance database is required.

## Decisions intentionally removed

- Multi-plugin ranking, selection, and version preference.
- Four package trust tiers and automated promotion/revocation.
- Independent publisher certificate/downgrade/rollback policy.
- A versioned implementation-module catalog and mandatory evidence locks.
- Generated design/code/test traceability as a phase gate.
- A public promise of forward/backward compatibility among atomically installed internal components.
- DeviceHost/IPC isolation and claims that it contained malicious same-user or administrator code.
- NativeAOT and native helpers whose only purpose was avoiding managed COM/WinRT.

These removals reduce failure surface. They do not remove any user-facing or SDK feature.
